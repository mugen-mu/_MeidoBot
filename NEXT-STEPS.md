1. **Первый запуск на живом боте — ждёт пользователя (~15 минут).** Код этапа 2 готов: `setup.cmd`, `README.md` по кликам, `npm run status`, `npm run export`, `LIVE-CHECKS.md` (12 шагов по 2 минуты). Что делает пользователь: приложение в Discord Developer Portal (README, шаг 1), двойной щелчок `setup.cmd` (вход в Cloudflare, три значения), три действия в Discord (адрес Interactions Endpoint URL, ссылки установки, `/setup`), по желанию сторож на healthchecks.io. Если что-то упадёт на живом — писать шаг и текст ошибки, чинит сессия по DiscordBot.
2. **Что подтвердит живой запуск** (в коде заложено с запасом): читается ли текст канала «бот» без постоянного соединения (если нет — «Личка» в `/settings`); значение «радио» в окне «На…» (читается `value` и `values`, запасной путь — строка «завтра 10:30»); окно из кнопки; команда-меню без описания; право «Управлять каналами» для `/setup`; push при упоминании; хватает ли 10 мс процессорного времени на запуск (панель Cloudflare → Workers → Logs, ищем «Exceeded CPU»); `wrangler d1 create --location eeur`, `d1 migrations apply` без вопроса, `deploy` в неинтерактивном режиме — установка писалась по справке wrangler, на настоящем аккаунте не запускалась.

9. **Характер 2: настроение и аниме-стиль (большое ТЗ пользователя 2026-11-07, исходники — `docs/personality/`, не править; начинаем после первого запуска и живых проверок).** Заменяет простую настройку из пункта 8 (она остаётся запасным нейтральным режимом). Адаптация под наш стек (в ТЗ Python, SQLite, YAML): модуль `src/personality/` на TypeScript с чистой логикой (`moodEngine.ts`, фразы и словарь как данные в коде, такая же структура `настроение → ситуация → фразы`, `config` с числами), состояние настроения в D1 (миграция 0002, на пользователя), настройки стиля в `settings`. События берём из наших состояний: «пропущено» = дело стало `overdue`, «вовремя» = `done` до просрочки, «с опозданием» = `done` после; «активность» = любое действие пользователя (кнопка, команда, текст в канале «бот»). Спад раздражения и симпатии считается при следующем событии (без работы cron), настроение — чистой функцией от времени. Команды из ТЗ: `/mood`, `/mood set`, `/reset_mood`, `/style`, `/hints`, `/glossary`; `/quiet` = наш режим «я в отъезде», но в часах. **Не получится на HTTP-боте:** статус бота (activity) и «печатает…» с задержками (нужно постоянное соединение), озвучка (в ТЗ «на потом»); вместо статуса — `/mood` и цвет embed. Картинки-спрайты настроений (6 штук) нужны от пользователя (Gemini), хранение — статические файлы Worker. Режим B (LLM) — позже и по желанию (бесплатный вариант проверить: Cloudflare Workers AI). Правило качества: суть напоминания (время, задача) всегда по-русски и читаемо, стиль выключается на серьёзных темах (самочувствие, горе). Этапы: Х1 — движок настроения, состояние, тесты по ТЗ §11, фразы для напоминания, «Готово», пропуска в 6 настроениях, `/mood`, `/reset_mood`, `/quiet`; Х2 — аниме-слой (уровни 0–3, словарь, SFX, каомодзи, подсказки перевода, `/style`, `/hints`, `/glossary`); Х3 — embed с цветом, спрайты, реакции, редкие «кино-моменты». Имя горничной по умолчанию «Хару» (настройка), приложение в Discord остаётся Meido. Вопросы к пользователю перед стартом: нет (умолчания приняты), поправит по ходу.

7. **Общий сервер с другом (2026-11-07: пользователь выбрал вариант Б, один бот на несколько областей; начинаем после первого запуска и живых проверок).** Сейчас бот одиночный: один хозяин (`meta.owner_id`), одни настройки (`settings`), один сервер (`meta.guild_id`), остальным «Этот бот личный». Два пути: (А) вторая независимая копия бота для сервера друга: новое приложение Discord + свой Worker и база, код не меняется, ~15 минут установки, обновления выкладываются в каждую копию; (Б) один бот на несколько «областей» (свой пользователь и каждый сервер со своими каналами, настройками, дела с владельцем): новая миграция, цикл cron по областям, проверка «кто это» в командах. Ответы пользователя (2026-11-07): что бот делает на общем сервере — пока неясно, зависит от того, что бот сможет в итоге; видеть дела друг друга — по настройке и «обоюдному согласию» (по умолчанию не видно); настраивает хозяин сервера (скорее всего). Для модели областей отсюда: по умолчанию всё личное, общий доступ к делам включается явно и с согласия обеих сторон; настройки сервера меняет хозяин сервера (или тот, у кого право «Управлять сервером»). Что именно делает общий сервер — решится позже, поэтому в схему областей закладываем гибко (владелец дела, область, флаг «общее»). Ничего не начато.
